# 目标 01：协议与安全边界

> 协议口径已确定；目标 02 已实现 CID 初始化、签发和上报策略，验证边界见[目标总览](前端错误监控目标总览.md)。事件接收和真实浏览器联调仍未完成。

## 目标与依赖

SDK 项目为 `message-reporting`，接收服务为 `app-pulse/backend`。本目标确定两端共同遵守的 v1 协议、安全边界、CID 签发记录和浏览器验收矩阵，并用独立实现验证公开加密向量。目标 02–06 以本文为准；目标 02 的代码及其验证状态单独记录。

## 初始化与地址

- `init` 必填 `serverUrl`、服务端分配的 `appId`，可选 `getContext`，动态上下文行为见[目标 05](目标05-环境与自定义上下文.md)。`sdkVersion` 由 SDK 自动提供，接入方不填写应用构建版本。
- `serverUrl` 为绝对 HTTPS 服务根地址，可以包含 API 路径前缀；仅 loopback 开发允许 HTTP（`localhost`、`127.0.0.1`、`[::1]`），不接受用户名、密码、查询或片段。通过 URL 解析规范化协议、主机和默认端口，移除末尾斜杠，保留路径大小写及路径前缀；后续接口以斜杠追加，不能用以 `/` 开头的相对 URL 覆盖前缀。
- 例如 `serverUrl=https://collector.example/custom-prefix`，签发地址为 `https://collector.example/custom-prefix/v1/cids`。后端前缀由其 `API_PREFIX` 配置，SDK 不写死默认值。
- `appId` 由 AppPulse 后端分配：管理员通过后台项目创建接口提交项目名称；后端使用密码学安全随机源生成 appId，保存项目名称与 appId 的对应关系后返回，供接入方配置 SDK。项目名称只作业务展示，不参与 appId 推导；后台页面和 SDK 不自行生成或指定 appId。项目管理接口已实现，后台页面待后续实现。
- `appId` 仅由 ASCII 小写字母 `a-z` 和数字 `0-9` 随机混合组成，必须至少包含一个字母和一个数字；协议长度为 2–64 字符。禁止大写、空白、下划线、连字符及其他特殊符号，不添加项目名称或固定前缀。后端用唯一约束保证全局唯一，随机碰撞时重新生成；格式合规不代表已创建，SDK 上报仍须校验服务端项目记录。项目改名不改变已有 appId。CID 本地存储按规范化 `serverUrl` 和 appId 隔离。

## HTTP 接口与响应

三个接口均使用 `POST` 和 `Content-Type: application/json`，不携带后台 Bearer 令牌。SDK 默认 `credentials: 'omit'`、`referrerPolicy: 'no-referrer'`，不使用 GIF、Beacon 或通道切换。

| 相对路径 | 请求体 | HTTP 200 的 `data` |
| --- | --- | --- |
| `v1/cids` | `{appId}` | `{cid}` |
| `v1/admission` | `{appId,cid}` | `{allowed: boolean}` |
| `v1/events` | 下述加密信封 | `null` |

统一响应为 `{code,message,data,timestamp,traceId?}`，`code` 为对应 HTTP 数字状态码，`timestamp` 为服务端 ISO 8601 UTC 时间；错误响应提供诊断追踪 `traceId`，它不同于 CID 和事件 ID。成功使用 HTTP 200，CID 签发是写操作返回必要业务数据的明确例外。示例：

```json
{"code":200,"message":"成功","data":{"cid":"AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8"},"timestamp":"2026-10-28T00:00:00.000Z"}
```

示例 CID 仅为公开测试值，真实签发必须使用安全随机源。接收端先限制请求体，再校验协议字段、CID 归属、当前上报策略、发送时间、认证标签和解密事件；最后原子去重并接受。请求字段按真实 JSON 类型校验，不依赖全局 DTO 隐式转换或静默丢弃非法字段。缺少必需字段、未知协议字段/版本、类型或规范编码不符均拒绝。

### 错误语义

| HTTP 状态 | `data.errorCode` | SDK 行为 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 丢弃本次事件，不重试；包含无效协议、认证标签、事件内容或发送时间 |
| 401 | `CID_INVALID` | 未签发、应用归属不符或已撤销；停止发送，按目标 02 安全清理本地 CID |
| 403 | `NOT_ALLOWED` | 停止发送，保留 CID；再次初始化后重新查询上报策略 |
| 409 | `REPLAYED` | 重复事件被拒绝，不重复写入、不重试 |
| 413、415 | `INVALID_REQUEST` | 请求过大或媒体类型不支持，丢弃本次事件 |
| 429 | `RATE_LIMITED` | 本次请求失败，不自动重试，不删除 CID |
| 500、503 等 5xx | 无，`data: null` | 保持后端通用提示，SDK 按 HTTP 状态归一为 `TEMPORARY_FAILURE`，按下述策略有限重试 |

4xx 示例为 `{code:401,message:'CID 无效',data:{errorCode:'CID_INVALID'},timestamp,traceId}`。未知与已撤销 CID 不返回内部记录或详细原因。代理、通用中间件或正文解析失败可能返回无协议错误码的错误；SDK 按 HTTP 状态作为失败处理，但普通 401 不能推断成 `CID_INVALID` 并删除 CID。网络失败、无效响应、中断和超时也不是成功。HTTP 200 但响应结构不符仍视为失败。

当前后端对控制器内识别的超大请求返回 413；超过正文解析器上限的请求在进入控制器前失败，通用异常处理返回 500，SDK 会按 5xx 策略有限重试。

上报策略查询结果为不允许时返回 HTTP 200、`data:{allowed:false}`；事件发送阶段禁止上报才返回 403。HTTP 200 仅表示协议约定的接受成功，不额外承诺未验证的最终持久化；网络异常或超时也不能证明服务端未处理。

### 超时与重试

- 三个 SDK 接口每次请求从发起到读取完整响应最多等待 5 秒；超时判定本次尝试失败并尝试中止，再按策略安排下一次尝试。一次操作最多初始请求 1 次及重试 3 次，即最多 4 次请求。
- 网络错误、单次超时和 HTTP 5xx 使用指数退避：第 1、2、3 次重试分别等待 1、2、4 秒，等待从前一次失败判定开始计算；等待期间停止或重新初始化时取消旧操作。HTTP 4xx（包括 429）、上报策略查询结果 `allowed:false`、无效响应及本地参数或存储错误不重试，避免对确定的拒绝持续施压。
- 事件重试原样发送同一份已加密信封，包括 `eventId`、`sentAt`、IV 和密文，不重新加密或创建新事件；服务端按事件 ID 原子去重。若先前请求已接受但响应丢失，重试可能返回 `409 REPLAYED`，SDK 停止重试并报告结果未知，不能据此承诺本次已成功或最终持久化。重试前如本地时间已超出 `sentAt` 的 5 分钟窗口则停止，服务端仍独立校验时间。
- CID 签发重试可能在先前请求已写入但响应丢失时创建多个签发记录；迟到响应不得覆盖已选用的 CID，未使用记录按服务端留存策略处理，频率限制仍生效。上报策略查询重试仍须取得合规的明确允许才可发送。超时、中止或迟到响应不证明服务端未处理；停止、重启或旧代次的响应不得改变当前状态。
- 事件请求最多 5 个实际未结束的请求，超时后即使尝试中止，底层请求实际结束前仍占名额；重试到时无法取得名额则停止该事件，不无界排队。缺少必要取消能力或请求长期无法结束时明确报告不可用或失败，不保证每次都能发满 3 次重试。

## CID 签发与业务记录

- 服务端安全随机生成 32 字节 CID，编码为无 `=` 填充的 base64url（43 个字符），保证签发唯一并绑定 `appId`。**签发记录持久化成功后才能返回 CID**；写入失败返回 503，不返回仅在内存中生成的 CID。
- 同一 CID 不设累计事件数上限，不因累计条数自动失效，也不维护累计额度或按累计量吊销。仍须逐次校验签发归属、有效状态、上报策略、协议及频率限制；CID 不证明真实用户身份。
- 服务端受控业务记录至少保存下表信息；它们不是签发响应字段，也不能由客户端请求体指定。

| 信息 | 来源与用途 |
| --- | --- |
| CID、所属 appId | 服务端生成及应用记录，用于唯一性和归属校验 |
| 创建时间 | 服务端写入，按后端规范使用 Unix 秒，不与事件的毫秒时间混用 |
| 签发来源 IP | 复用后端 `getClientIp`，兼容 IPv4/IPv6，用于追溯及申请限流 |
| Origin、UA | 签发 HTTP 请求中实际可获得时保存并限制长度；缺失时为空，不回退采集完整 Referer |
| 有效/撤销状态、撤销时间及原因 | 受控管理操作，撤销时间使用 Unix 秒；原因不透传 SDK |

- 签发 IP 是创建时快照，不绑定后续上报。切换网络或 IP 不使合法 CID 自动失效；Origin 和 UA 可伪造，也不作为可信身份。
- 每个 appId 独立维护 CID 黑白名单；上报策略支持全部允许（黑名单除外）、仅白名单与黑名单拒绝，新建项目默认使用白名单，黑名单在所有策略下均拒绝。名单互斥，加入另一名单前须由管理员先移除原名单，否则接口拒绝并提示。支持人工撤销；后续事件接收须逐事件检查最新策略，不能信任 SDK 缓存的允许状态。
- 签发请求按 appId 与客户端 IP 限制成功申请（默认滚动 24 小时最多 10 个，阈值维护在后端日志上报协议常量中），同时限制失败申请、上报策略及事件请求频率。这不是 CID 累计事件额度。
- 实体遵循后端规则，包含内部主键、创建/更新及软删除字段，不对外暴露内部主键；共享环境建表按后端数据库结构策略单独执行。

## 加密事件协议

信封为 `{version:1,appId,cid,eventId,sentAt,iv,ciphertext}`：

- `eventId`：客户端为每条新事件安全随机生成 16 字节，无填充 base64url（22 个字符）。
- `sentAt`：加密发送时的 Unix 毫秒安全整数；发生时间为加密事件中的 `occurredAt`，同为 Unix 毫秒安全整数。
- `iv`：每条事件安全随机生成 12 字节，无填充 base64url（16 个字符）。
- `ciphertext`：AES-GCM 密文后直接拼接 16 字节认证标签，整体编码为无填充 base64url，不另设标签字段。

所有 base64url 字段严格校验字符、解码长度和重新编码一致性；拒绝填充、非规范尾部位、标准 base64 字符、空值及错误长度。

### 两端独立派生子密钥

| HKDF-SHA-256 参数 | 精确定义 |
| --- | --- |
| 输入密钥材料 IKM | 解码后的 32 字节 CID，不使用 CID 字符串的 UTF-8 字节 |
| salt | UTF-8 `message-reporting/v1` |
| info | UTF-8 `aes-256-gcm:` + `appId` + `:` + `eventId`（规范编码字符串） |
| 输出 | 32 字节 AES-256-GCM 子密钥 |

AAD 为紧凑 JSON 数组 `[1,appId,cid,eventId,sentAt]` 的 UTF-8 字节，按此顺序、无空白序列化；字符串均为规范 ASCII，整数用普通十进制。使用 128 位标签，解密或标签校验失败即拒绝。参数含义参考 [Web Crypto 规范](https://www.w3.org/TR/webcrypto/)。

每条新事件的 `eventId` 参与派生，无需获取密钥的新接口，也不保存每条派生密钥；不能实现成每 CID 缓存一个长期 AES 密钥。同一派生密钥下不得重复使用 IV；不同事件子密钥不以 CID 范围的 IV 相同作为拒绝依据。固定 IV 仅用于公开向量测试，生产使用安全随机值；随机 ID、密钥和 IV 不作数学上的绝对不碰撞保证。

明文事件至少包含 `schemaVersion:1`、`eventId`、`appId`、`sdkVersion`、`occurredAt`、`kind`、`message`，详见[目标 03](目标03-事件与加密发送.md)。明文与信封的 `appId`、`eventId` 必须一致；明文 UTF-8 JSON 不超过 32 KiB，完整信封 JSON 不超过 48 KiB。先有界整理字段，仍不合规时丢弃，不截断成无效 JSON。

### 去重与时间窗口

服务端校验 `sentAt` 在当前时间前后各 5 分钟以内，对 `(appId,cid,eventId)` 原子去重，成功接受后至少保存 10 分钟；去重与接受须具有一致的原子语义。保留期不得短于完整接受窗口。不按 CID 永久累积 IV 列表。同一事件 ID 的并发请求最多接受一次；重试只能复用原信封，不能为同一事件 ID 加密不同内容。

## 安全、日志与失败边界

- CID 在信封中可见，持有者可派生事件密钥、解密捕获的信封或构造新事件。AES-GCM 不提供对 CID 持有者的保密性或可信身份；HTTPS、签发校验、上报策略、限流和审计各自承担职责，不能保证阻止分布式刷写。
- 保留后端 `trust proxy: true`，来源 IP 由 Express 解析。部署须保证代理链正确清理/重写转发头；否则客户端可影响解析 IP，不能承诺 IP 限流可靠。参见 [Express 代理说明](https://expressjs.com/en/guide/behind-proxies/)。
- 允许明确配置的应用来源进行 CORS 预检和 JSON POST；生产来源白名单须部署前提供，不以示例域名验收。CORS 不是访问控制，无 Origin 的直接 HTTP 请求仍须经过相同业务校验。
- 必要签发存储、限流、上报策略校验或去重组件不可用时返回 503，停止接受本次请求；不能照搬后端通用限流在 Redis 故障时放行的行为。其他接口的现有策略不在本目标范围。
- SDK 接口和后台管理接口使用后端通用日志和异常处理规则，访问日志可能记录包含 CID 的请求或响应正文、查询参数及 Referer；通用异常诊断会记录错误信息和请求地址。部署后的日志链路仍须验证。
- 默认不主动采集 Cookie、令牌、请求体、完整 URL 查询参数或片段。签发 Origin/UA 与事件有限环境信息分别说明用途；业务错误、路径和上下文仍由接入方脱敏。服务端访问控制、留存和删除策略须部署前落实。
- 缺少安全随机源、Web Crypto、可读写持久存储、Fetch、UTF-8 编解码、base64url 编解码或必需监听能力时，初始化返回明确不可用状态，不发送明文，不影响宿主。Web Crypto 需要安全上下文；不能仅根据 UA 或 ES2019 语法目标推定能力。
- 单次请求超时 5 秒，按上述指数退避最多重试 3 次；最多 5 个实际未结束的事件请求，超限停止。无离线队列或退出投递保证。Source Map 上传、存储和还原不属于本轮实现或验收。

## 离线验证与后续验收

公开向量位于 SDK 的 `tests/fixtures/protocol-v1.json` 和后端的 `test/fixtures/protocol-v1.json`，内容须一致，包含固定 CID、appId、事件 ID、IV、时间、明文、派生密钥、AAD 和密文/标签；均非生产凭据。固定向量不得用于真实发送。

- SDK `tests/protocol.test.mjs` 使用 Web Crypto，后端 `test/protocol.test.mjs` 使用 Node crypto。两端独立验证同一固定输出，各自运行不依赖另一仓库，也不共享加密实现；这些是测试专用计算，不是生产协议实现。
- 验证中文和多字节 UTF-8、子密钥随事件 ID/应用/CID 改变、跨实现密文解密、规范编码/长度、错误密钥及 AAD/密文/标签篡改拒绝。
- SDK 执行 `npm run check`，后端执行 `pnpm run test`；定向命令分别为 `node --test tests/protocol.test.mjs` 和 `node --test test/protocol.test.mjs`，在各自目录运行。

后续真实接口验收必须覆盖：签发唯一及持久化失败不返回 CID；来源信息与跨 IP 使用；同 CID 连续接受事件且无累计额度；上报策略及撤销；无效/跨应用 CID；成功和失败请求限流；组件故障拒绝；5 秒超时、1/2/4 秒退避及最多 3 次重试、停止与迟到响应、签发响应丢失后的多记录、事件响应丢失后的原信封重试及 409 未知结果；原子并发重放；过去/未来时间边界及偏差；消息超限；访问日志记录行为及跨域预检。并发、额度和持久化不能用离线加密测试冒充已通过。
